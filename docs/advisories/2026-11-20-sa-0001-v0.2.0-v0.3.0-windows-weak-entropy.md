# HoloNet-SA-0001: Predictable entropy on Windows builds of v0.2.0 / v0.3.0

- **Advisory ID:** HoloNet-SA-0001 (self-assigned)
- **Also published as:** GitHub Security Advisory
  **GHSA-8h6m-w5qj-cq9g** (published 2026-11-20;
  https://github.com/maniesh-NR/HoloNet/security/advisories/GHSA-8h6m-w5qj-cq9g);
  a CVE was requested on publication (id assigned asynchronously by
  GitHub and will appear on the advisory page).
- **Date:** 2026-11-20
- **Severity:** Moderate (attack vector: local)
- **Reported by:** internal adversarial review, gate 0001 (A1-C1);
  publicly disclosed in `docs/THREAT-MODEL.md` §G from the day of
  discovery — this advisory formalizes it per decision D-0025.

## Summary

Release binaries for Windows built from the `v0.2.0` and `v0.3.0`
tags predate the fail-closed entropy hardening (commit `53ff229`,
2026-11-13). On Windows those builds have no `/dev/urandom`; their
non-security PRNG fell back to splitmix64 seeded with
`time ^ pid ^ counter` — and the security-material call sites of that
era still used the weak source. Two kinds of material were affected:

1. **AEAD session salts** (`random_salt()` in the Shadowsocks plane) —
   predictable salts weaken session-key derivation for captured
   sessions: a local attacker who can read relayed traffic and who
   knows (or guesses) the wall-clock time and process id can recover
   the derivation input.
2. **The daemon IPC authentication token** (`ensure_token()`) — a
   predictable token lets any local process authenticate to the daemon
   (`127.0.0.1:7977`) that the victim's own client would also use.

## Affected artifacts

- `holonet-v0.2.0-windows-*.zip` and `holonet-v0.3.0-windows-*.zip`
  (Windows x64 + x86 builds from the `v0.2.0` / `v0.3.0` tags).

**Publication history, stated precisely:** these artifacts existed as
maintainer-visible GitHub release **drafts** only (API-verified
2026-11-20; the release workflows' "success" conclusions had uploaded
to drafts — the defect reconciled in D-0013/D-0025). Whether any
public-download window existed earlier is unknowable; the artifacts
were not publicly downloadable from at least 2026-11-17, and the
drafts holding them were deleted on 2026-11-20 rather than republished
(republishing would have rebuilt vulnerable code).

## Not affected

- Unix builds of any version (`v0.2.0-linux`, the macOS/Android
  artifacts): the same code path reads `/dev/urandom`, which exists on
  those platforms — the weak fallback never engaged. The fail-closed
  behavior (hard error instead of any fallback) was added by the same
  `53ff229` remediation.
- Anything built from `53ff229` (2026-11-13) onward, including
  **v0.3.1** — the first tagged release from the hardened tree.

## Remediation

- **Fixed:** commit `53ff229` (2026-11-13, gate-0001 remediation;
  D-0008): Windows entropy via RtlGenRandom (SystemFunction036)
  through advapi32, available since Windows XP so the Windows 7 SP1
  floor is covered; any syscall failure is a hard error — the engine
  refuses to generate security material rather than degrade.
- **Upgrade:** run **v0.3.1** or later (checksums: per-release
  `SHA256SUMS.txt`; release-manifest signature: see README
  "Verifying release signatures").
- **If you ran an affected Windows build:** upgrade, then delete the
  daemon's `ipc-token` file in the data directory (it is regenerated
  on next start) and reconnect your sessions.

## Workarounds

None for the affected binaries other than upgrading; the weak source
is the only entropy source they have on Windows.
