## 1. D-0009 — I independently verified the factual basis, and it is worse than "predictable seed"

- At tag `v0.3.0`: `random_salt()` called `holo_util::rand::fill` (splitmix fallback on Windows) — `git show v0.3.0:engine/crates/holo-ss/src/lib.rs:905-909`; `ensure_token()` used `rand::hex(24)` with **no 0600 tightening** — `git show v0.3.0:engine/crates/holo-engine/src/lib.rs:73`; release workflow had **zero** checksum steps (`git show v0.3.0:.github/workflows/release.yml`, sha256 count = 0). Unix builds at those tags were fine (old `next_u64` preferred `/dev/urandom`).
- Exploitability analysis (suspected, but grounded in the verified seed construction `nanos ^ pid<<32 ^ counter`, current `rand.rs:36-42`): with millisecond clock sync + Windows PID space, the seed is offline-brute-forceable from **one** captured 32-byte salt (~2^25–2^30 candidates); and the splitmix64 mix is fully invertible, so one salt recovers the internal state and predicts **all** future PRNG output of that process.
- Honest impact scoping: the salt is wire-public per SIP004, so content keys are NOT recoverable — **not a confidentiality break**. The real harms in a censorship context: (a) passive DPI can positively **fingerprint the tool** by correlating consecutive salts (splitmix state continuity) → "this user runs an anti-censorship tool"; (b) **cross-session linkability** of one installation across servers/destinations; (c) local cross-user attacker predicts the **IPC token** (pre-0600 at those tags) → daemon control → proxy passwords/WG private keys via profiles.
- **README.md:86-89 still advertises `v0.2.0-windows` downloads with no warning** — the only disclosure lives in THREAT-MODEL §G (`docs/THREAT-MODEL.md:132-138`) and `harness/memory/STATE.md:30`.

**Recommendation**: publish a GitHub security advisory **now**, scoped to Windows binaries of v0.2.0/v0.3.0 only, with the three-part honest impact statement above; **do NOT cut v0.3.1 before S1 item 0 lands** — Windows builds from the current tree fail closed and cannot dial at all (`random_salt` errors out, `holo-ss/src/lib.rs:913-921`; `ensure_token` errors, `holo-engine/src/lib.rs:74-77`), so a v0.3.1 cut today ships an unusable Windows client. When the FFI lands, cut v0.3.1 — all four release jobs already emit SHA256SUMS.txt (verified `release.yml:53,99,145,209`). The hybrid "delete bad assets + advisory": delete **only the Windows zips** (dangerous artifact, checksum-less, fingerprintable), never silently; keep tags and other platforms for the audit trail. Real-world norm for shipped-weak-RNG (Debian OpenSSL 2008 class): advisory + mitigation + fixed release — deleting assets outright is the outlier, and for this threat model removing only the affected platform's artifacts is the defensible middle. Until the owner decides, add a warning line to the README download table (cheap, no gate needed).

## 3. S1 crypto plan, item by item

- **(a) X25519** (`ROADMAP.md:61-65`): the policy (all-zero-reject only, accept non-canonical u) matches RFC 7748-era guidance and modern practice (Go `crypto/ecdh`, BoringSSL, libsignal all check the all-zero output and do not reject non-canonical u; RFC 7748 §5 masks bit 255 and §6 requires processing non-canonical values mod p — RFC text quoted from reviewer knowledge, **not re-read in sandbox: suspect, must be quoted verbatim when drafting**). Two risks: the words "accepted as-is" can be misread as "skip bit-255 masking / skip reduction" (wrong — decode per RFC 7748 §5 still applies); and the charter never says the all-zero compare must be constant-time (`ct_eq` exists, `holo-crypto` — one clause fixes it).
- **(b) AES-CFB** (`ROADMAP.md:66-68`): "forbidden outside an authenticated wrapper" is **prose only** — no grep-audit step in `ci.yml`, no API-shape rule. Contrast: the unsafe-grep criterion at least has a defined command; CFB has neither mechanism nor registry. Mechanize it (CI grep for `cfb` outside the wrapper module + raw CFB types not `pub`).
- **(c) bignum/CIOS/RSA verify** (`ROADMAP.md:71-73, 107-110`): the final-carry-limb pitfall is *noted* but the acceptance ("published Montgomery test vectors") would not necessarily exercise the final carry — require carry-triggering boundary vectors (modulus top limb all-ones, operand = R−1). Missing entirely: PKCS#1 v1.5 **negative** tests (hash mismatch, trailing garbage — Bleichenbacher '06/BERserk class), PSS wrong-salt-length, wrong EM length; and any CT/usage scoping: verify takes public inputs (blinding genuinely unnecessary — say so explicitly) but nothing forbids reusing a branchy bignum for secret scalars later (X25519 in S2 is secret-scalar). Charter should record "verify-only, public inputs; signing forbidden without a new decision + blinding" and a branch-free requirement (or explicit non-goal) for secret-scalar arithmetic.
- **(d) Windows FFI containment** (`ROADMAP.md:93-99`): the grep criterion is defined but **nothing in CI runs it** (`ci.yml:11-122` has no such step) and only 5 of 11 crates carry `#![forbid(unsafe_code)]` today (grep-verified: holo-ss:21, holo-net, holo-socks, holo-crypto, integration tests). The legacy-toolchain job checks the **ubuntu host** only (`ci.yml:108-122`) — the "Windows 1.77.2 compile check" must actually be added (`cargo check --target x86_64-pc-windows-msvc`) or the windows job pinned to 1.77.2 (windows job runs stable, `ci.yml:25-28`). Failure-injection seam is chartered but must cover **both** dynamic-load failure (GetProcAddress null on a stripped box) and call failure; the charter names RtlGenRandom/BCryptGenRandom without a selection rule (ProcessPrng is Win10-1809+/Win11-era — not on the Win7 floor; RtlGenRandom is right there but is an undocumented API with a standing MS removal warning — pick the order explicitly).
