# AGENT A2 — Security Red — Gate 0001 (S0 → S1) Hostile Review

## 1. Entropy — the sharpest issue, and it is real

**The only randomness source in the engine** is `engine/crates/holo-util/src/rand.rs`. Verified facts:

- `rand.rs:16` opens `/dev/urandom`, reads 8 bytes **per call**, and on *any* open/read failure silently falls back to `splitmix64(nanos ^ pid<<32 ^ counter)` (`rand.rs:23-29`). This is **fail-open**: there is no error, no log, no distinction between "got OS entropy" and "got a time-seeded PRNG".
- `/dev/urandom` does not exist on Windows. Windows 7–11 is a first-class release target with prebuilt binaries shipped today (`README.md:8,82`; `.github/workflows/release.yml:20-60`). **On every Windows install, all "random" material is splitmix64(time, pid, counter)** — predictable, brute-forceable (file mtime narrows time; PIDs are enumerable; the counter sequence is deterministic).
- Consumers, traced via grep of `rand::`:
  - **Crypto material (bad):** `holo-ss/src/lib.rs:905-907` `random_salt()` → SIP004 session salt, used at `lib.rs:331` (client) and `lib.rs:609` (server). Salt feeds HKDF subkey derivation (`lib.rs:71`). Salt need not be secret but must be unique; more importantly the same module generates the…
  - **Security-critical auth material (worse):** `holo-engine/src/lib.rs:73` `ensure_token` → the IPC auth token (24 bytes hex) guarding the control channel on 127.0.0.1:7977.
  - Non-security: `holo-config/src/lib.rs:128-130` profile IDs.
- **Attack chain (suspected, feasibility argued from verified code):** predictable Windows IPC token → any local process authenticates (`holo-engine/src/lib.rs:484-487`) → `profiles.list` returns full `params` including the Shadowsocks `password`, trojan/hy2/tuic passwords, WireGuard `private_key`/`preshared_key` (`holo-engine/src/lib.rs:525-533`; `holo-config/src/lib.rs:70-93`; `holo-config/src/links.rs:148,153,247,291,312,321`) → recorded traffic decryption / server credential theft. On a machine shared with stalkerware or a hostile "IT admin" — a realistic scenario for this user population — that is a direct physical-risk amplifier.
- **The gap is acknowledged nowhere.** Repo-wide grep for `urandom|getrandom|RtlGenRandom|BCryptGenRandom|SecRandomCopyBytes|entropy|CSPRNG` hits only `rand.rs:1` and `rand.rs:16` themselves. Not in `docs/TECHNIQUES.md` §9, not in `harness/memory/`, not in the S1 charter (`harness/memory/ROADMAP.md:38-61`).
- **Why this gate specifically:** S1 is titled "the primitives the TLS/QUIC stages need" (`ROADMAP.md:40`) and introduces **X25519** (`ROADMAP.md:43-44`). RFC 7748 vectors will pass while production keygen on Windows remains predictable — i.e., the S1 acceptance criteria are *structurally incapable of catching* the most catastrophic failure mode of the very primitive being added. And the charter's "no unsafe; no new third-party crates" rule (`ROADMAP.md:59-60`) makes the Windows fix *impossible in pure std* — there is no std CSPRNG API and no `/dev/urandom`. That policy conflict (audited unsafe FFI to `RtlGenRandom`/`BCryptGenRandom`? frontend-fed entropy? drop Windows?) is a **gate-level architecture decision**, not an S2 implementation detail. Passing this gate without resolving it entrenches a broken foundation into key agreement.

## 2. Constant-time posture — partially done, undocumented

- Good, verified: `#![forbid(unsafe_code)]` (`holo-crypto/src/lib.rs:21`, `holo-ss/src/lib.rs:18`); `ct_eq` OR-accumulation exists (`holo-crypto/src/lib.rs:661-670`) and is used in both AEAD verify paths (`lib.rs:600`, `lib.rs:987`).
- Bad, verified: **AES is table-based** — S-box lookups at secret-dependent indices (`holo-crypto/src/lib.rs:755,760` and round code) = classic cache-timing exposure; GCM is a live cipher for the data plane (`holo-ss/src/lib.rs:103`). The IPC token comparison is a plain `!=` (`holo-engine/src/lib.rs:485`). No document anywhere states the side-channel adversary model or scope (grep across `docs/`, `README.md`, `harness/` for `side.?channel|timing|constant.?time` → only unrelated hits). For a censorship-resistance tool, "RFC/NIST vectors pass" is a correctness bar, not a security bar; the threat model must state honestly that remote timing is out of scope but local co-residency is (or isn't) accepted. Absence is the finding.

## 3. Threat model — absent

No document defines the adversary (DPI box? GFW-style active prober? local endpoint compromise? upstream observer?) or maps defenses to it. `docs/TECHNIQUES.md:140-160` motivates padding and probe-resistance with literature citations (good) but never states what adversary capabilities are in/out of scope. `docs/ARCHITECTURE.md` and `README.md` contain no adversary model. For a tool whose users can face physical risk, this is a required artifact before building key agreement (S1) and TLS (S2), because every design call downstream (CT requirements, rekey intervals, pinning policy, logging) depends on it.

## 4. Anti-probing claims vs. actual code

Verified by reading `holo-ss/src/lib.rs` and `holo-net/src/lib.rs`:

- Oversized-length rejection is real: threshold `MAX_PAYLOAD = 0x3FFF` (`holo-ss/src/lib.rs:29`), checked at `lib.rs:288-289`, mapped to the single opaque `auth_failed()` (`lib.rs:297-300`). Error text is opaque — good.
- **"Randomized slow-close" is not randomized.** `serve_conn` sleeps `delay.min(120ms)` (`holo-ss/src/lib.rs:760-763`) where `delay` is deterministic `50ms·2^n` from `ProbeGuard::on_failure` (`holo-net/src/lib.rs:755-765`). No RNG anywhere in the failure path. Claims at `README.md:44`, `docs/TECHNIQUES.md:156`, and the crate doc `holo-ss/src/lib.rs:12-14` ("randomized slow-close", "never leaking whether the failure was salt, length, or payload") are **false as implemented**.
- **The 10 s backoff cap is dead on the wire.** `docs/TECHNIQUES.md:154` claims "50 ms doubling, 10 s cap"; `ProbeGuard` computes up to 10 s, but the sleep is clamped to 120 ms (`holo-ss/src/lib.rs:763`). A prober never experiences more than 120 ms.
- **Timing distinguisher (verified mechanism, suspected exploitability):** if the decrypted length is valid (≤0x3FFF), the server blocks in `read_exact` for `len+16` payload bytes (`lib.rs:291`); if the length tag fails or length is oversized, it closes after the fixed short sleep without waiting. A prober sending only the 18-byte length chunk can therefore distinguish "length decrypted and was in-range" from "length rejected" purely by close-vs-hang — precisely the "response timing" channel `TECHNIQUES.md:145-147` says probes exploit.
- `ProbeGuard.last` is written (`holo-net/src/lib.rs:763`) and removed (`:770`) but **never read** — no decay, no eviction; `attempts` grows unboundedly per distinct failing peer IP (memory DoS on a long-running server). Mitigating context: `serve_conn` is currently exercised only by tests (`holo-engine/tests/integration.rs:61`, `holo-ss/src/lib.rs:950,1053`) — the shipped daemon runs the SS *client*, not the server.

## 6. Secrets at rest / local attack surface (current binaries)

- `ipc-token` (`holo-engine/src/lib.rs:74`) and `profiles.json` (containing all credentials, `holo-config/src/lib.rs:212-214,229-232`) are written with plain `std::fs::write` — **no permissions hardening anywhere** (grep `set_permissions|PermissionsExt` → zero hits in `engine/`). Default umask 022 on multi-user Linux → world-readable proxy passwords and IPC token.
- The local SOCKS5 listener has RFC 1929 support (`holo-socks/src/lib.rs:219-220`) but the engine binds it with **no auth** (`holo-engine/src/lib.rs:290-293`) and `proxy_listen` is user-settable to a non-loopback address with no warning → open-relay footgun.
- IPC token check is not constant-time and `hello` has no rate limit (`holo-engine/src/lib.rs:484-487`) — low severity while the token is strong, compounding if it is predictable (§1).

## 7. S1 charter security adequacy

- X25519: all-zero rejection is specified (`ROADMAP.md:43-44,51-53`) — that covers small-order points (they yield all-zero output), but the charter should record the **contributory-behavior policy** explicitly (zero-check only, TLS 1.3 style, with non-canonical `u` acceptance documented) so S2/S3 inherit a decision, not an accident.
- AES-CFB is fine as a primitive, but "legacy provider paths" (`ROADMAP.md:45`) must be constrained by charter language: CFB is unauthenticated; any use outside an authenticated wrapper should be forbidden.
- **Sequencing gap (verified from charter text):** S2 requires RSA CertVerify "PKCS#1 v1.5 + PSS via CIOS Montgomery bignum" and SPKI pinning (`ROADMAP.md:63-70`), yet none of the bignum/signature-verification primitives are staged in S1 — the stage explicitly defined as the dependency-ordered primitive layer (`ROADMAP.md:40`). Either the dependency analysis is wrong or S2 will do primitive-building under a protocol gate with weaker vector coverage. Flag now, not at gate 0002.
- ExpandLabel as a standalone primitive is reasonable; its acceptance vectors are adequately specified (`ROADMAP.md:54-56`).

## 8. Release / supply-chain integrity

- Checksums: **only the Linux job** emits `SHA256SUMS.txt` (`.github/workflows/release.yml:141,150`). Windows (`:50`), macOS (`:94`), Android (`:202`) publish archives with **no checksums at all**. Verified.
- No signing story anywhere; `README.md:72-88` ("Binaries are portable: unpack and run") never tells users to verify anything. For a censorship-resistance tool distributed to users on hostile networks, a substituted binary is total compromise (all traffic + local files). Also: GitHub-hosted checksums alone are not MITM-proof, but they enable out-of-band verification; their absence on 3 of 4 platforms is indefensible.
- CI pins Rust 1.77.2 but floats action tags (`actions/checkout@v4` etc., `release.yml:28,72,114,161`) rather than SHA-pinning — standard-practice nit, noted for completeness.

Strict-fail logic (opaque single error, oversized-length conflation, wrong-password clients never reaching the upstream dialer, tested at `holo-ss/src/lib.rs:1041-1078`) is genuinely implemented in the error-value dimension. No `unsafe` anywhere in shipped crypto paths. No tracked secrets.
